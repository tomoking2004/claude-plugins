# claude-plugins

[![scan](https://github.com/tomoking2004/claude-plugins/actions/workflows/scan.yml/badge.svg)](.github/workflows/scan.yml)

Claude と Claude Code のプラグインのマーケットプレイス．全プラグインを一つの美の基準（美の6条．[plugins/refine/BEAUTY.md](plugins/refine/BEAUTY.md)）で貫く．

## なぜ

- **確定版＝不動点**：refine プラグインは，走査（決めた項目を全件確かめること）で見つかる欠陥がゼロになるまで成果物を磨いて確定する．目指す先は，再び適用しても変わらない形（不動点）である．このリポジトリ自身も，走査のうち機械で判定できる部分は，再実行可能な検査（[scripts/scan.py](scripts/scan.py)）でゼロを確かめる．
- **一つの基準が全媒体を貫く**：コード・文書・コミットが同じ美の6条で仕上がる．
- **知能を償却する**：一度見つけた判断を走査の規律（何を見て何を確かめるか）へ固めるので，日々の仕上げにトップ級の知能は要らない．
- **完璧が自己進化する**：基準そのものが磨かれ，良くなった分は以後の全ての成果物に効く．

## 仕組み

「完璧」は二層で保たれる．

- **実行**：スキル（Claude が従う手順の定義）は判断を走査の規律に還元する．だから一定の能力があればどのモデルでも，同じ走査で同じ確定版を目指せる．
- **進化**：走査の規律で捉えきれない観点が現れたら，heal プラグインのスキル（/heal:heal-skill）が規律そのものを直し，以後は全モデルがそれを継承する．

## プラグイン

プラグインは，[plugins/](plugins/) 直下のディレクトリに一つずつ入っている．役目・導入・使い方は，それぞれの README.md が述べる．

## 導入

対応先（Claude Code だけか，Claude でも使えるか）と依存先は，各プラグインの README.md の「導入」が示す．

### Claude Code

次を実行する．`<plugin>` は導入するプラグインの名前（`plugins/` 直下のディレクトリ名）に置き換える．依存先は併せて入る．

```text
/plugin marketplace add tomoking2004/claude-plugins
/plugin install <plugin>@tomoking2004
```

### Claude

Claude（claude.ai とデスクトップアプリのチャット・Cowork）では，有料プランで次の順に追加する．

1. Customize > Plugins > Add > Add marketplace に `tomoking2004/claude-plugins` を入れる．
2. 使うプラグインを追加する．Claude Code 専用のプラグインは追加できない．
3. 依存先も同じ手順で追加する．

追加したプラグインは，同じアカウントでサインインした Claude Code にも同期される．その Claude Code に同名のプラグインを `/plugin install` で導入して有効にしてあれば，導入した版が優先される．同期されたプラグインの依存先は，Claude でも追加しておくか，Claude Code で `/plugin install` して有効にしておく——Claude Code の[公式文書](https://code.claude.com/docs/en/plugin-dependencies)が，プラグインの作者にそう案内するよう求めている．

チャットでは，`/` のメニューからスキルを選ぶか，依頼を言葉で書く．チャットからは手元のファイルにも git リポジトリにも触れないので，対象は会話に添えて渡す．使える範囲はプラグインごとに異なり，各プラグインの README.md の「導入」が示す（Cowork での範囲は定めていない）．

## 開発

### 構成

- プラグイン＝`.claude-plugin/plugin.json` を持つ，`plugins/` 直下のディレクトリ．スキルは `plugins/<plugin>/skills/<name>/SKILL.md` に置く．
- プラグインの紹介は `plugins/<plugin>/README.md` が持つ．表題はプラグイン名，冒頭の段落は `plugin.json` の description と同じ文とし，「導入」（対応先と依存先）と「使い方」の節を置く．そのプラグインに固有の開発の事柄があれば，「開発」の節に書く．本書はどのプラグインも紹介しない——プラグインを足しても，本書を直さずに済む．名指すのは，プラグインをまたいで働く refine（美の基準）と heal（定義の治療）だけである．
- スキルを持つプラグインは一つの軸（工程・媒体など）を持ち，スキルはその軸の上に並べる．どの軸にも乗らないスキルが現れたときだけ，プラグインを新設する．
- 媒体をまたぐ委譲元スキル（範囲を媒体へ分解し各媒体スキルへ委譲するもの）の置き場は，領域固有性で決める．束ねる役が特定の領域に固有なら，その領域のプラグインに内包する．どの領域にも属さなければ refine の外のプラグインに置き，refine は純粋な媒体軸に保つ．
- スキル名は組み込みコマンド名（/context ・ /review ・ /init ・ /status 等）と一致させず，プラグインをまたいでも重複させない——素の名前（名前空間を除いた名前）はマーケットプレイス全体で一意に保つ．プラグインのスキルは `/<plugin>:<skill>` のほか素の名前でも呼べるが，素の名前が効くのは他のコマンドがその名を使っていないときだけである．
- スキル名は「動詞-目的語」の形（refine-code・heal-skill）にそろえ，素の名前だけで役目が分かるようにする．先頭に置ける動詞は scan.py の `SKILL_VERBS` が持つ．
- スキル内の相対リンクはプラグイン境界を越えられない——導入時はプラグインごとに `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/` へ個別展開されるため，他プラグインのファイルを指す `../../../` は解決しない（このリポジトリ上では通るので気づきにくい）．他プラグインの規則に従わせるには，パス参照ではなくそのプラグインのスキルへ委譲し，`dependencies` に宣言する．
- heal の外のスキルは，失敗時に /heal:heal-skill を呼ぶ．そのスキルを持つプラグインは，heal を `dependencies` に宣言する．
- 画面拡張（mod）は，`hooks/hooks.json` が名指す TypeScript のモジュールに置く．mod だけから成るプラグインは，スキルも軸も持たない．
- 配布する定義を直す先は常にこのリポジトリ．導入済みの実体（`cache` 配下）を書き換えても，プラグインの更新で上書きされて消える——/heal:heal-skill もこの区別に従う．利用者固有の好み・事実は配布する定義でなく，利用者のプロジェクト側に置く．

### 美の基準

美の基準は [plugins/refine/BEAUTY.md](plugins/refine/BEAUTY.md) が唯一の定義元．実行時に適用するスキルはその場でこれを読む．他のスキルの扱いは成果物で分かれ，分かれ目は同書が定める．

- 外へ出す成果物がファイルとして残るなら，美の規則（その媒体でどう書けば美しいか）を refine の媒体スキルへ委譲し，委譲元は領域の規則（何を満たせば目的に適うか）だけを持つ．
- 提案の中にしか存在しない文面（コミット・リリースノート）のように，refine の媒体スキルが掴めない成果物を作るスキルは，美の基準を自らの媒体へ具体化して自足する．
- プロジェクトの内側に留まる成果物（`.claude/context.md`・SKILL.md 等）は，後の全体の仕上げに委ねる．

### Claude への対応

- Claude でも使うプラグインは，チャットでも読み込まれる部品（スキル）で組む——hooks と agents はチャットでは無視される．
- プラグインの最上位に `bin/` があると，Claude はそのプラグインを追加できない．Claude Code 専用のプラグインにだけ `bin/` を置く．`plugin.json` には対応先（Claude か Claude Code か）を宣言する項目が無いので，`bin/` で追加を止める．専用のプラグインの一覧は scan.py の `CLAUDE_CODE_ONLY` が持つ．
- `dependencies` は `<plugin>@<marketplace>` の形で書く．Claude から同期された版はマーケットプレイスに属さない．Claude Code の公式文書は，その版の依存が満たされる条件を，マーケットプレイス名付きの指定についてしか定めていない．だから名前だけの指定は，同期された版で満たされる保証が無い．
- スキルの外にあるプラグイン内の文書（BEAUTY.md 等）も，チャットで読める——実機で確かめた挙動である．

### 手元での読み込み

開発中のプラグインは，`claude --plugin-dir plugins` で作業ツリーの版を読ませる．全プラグインが読まれ，同名の導入済みの版より優先される．SKILL.md の編集は，遅くとも次セッションか `/reload-plugins` 後に反映される．検証では，マーケットプレイス版を導入したときと同じ `/refine:refine-code` 形式で呼び出す．

### 不変条件の走査

このリポジトリの不変条件は [scripts/scan.py](scripts/scan.py) が走査する．scan.py は BEAUTY.md の「ゼロ確認」を，印象でなく再実行可能な検査として持つための道具である．

| 検査 | 確かめること |
| --- | --- |
| 構成 | マニフェストとディレクトリ構成の一致，SemVer，`dependencies` の形式と実在，SKILL.md の frontmatter，素の名前が「動詞-目的語」の形で，組み込みコマンドと衝突せず一意であること．`bin/` を持つプラグインが `CLAUDE_CODE_ONLY` と一致すること |
| 文書 | 相対リンクが実在してプラグイン境界を越えないこと．動的コンテキスト（読み込み時に走るコマンド）が代表的な git 状態で exit 0 かつ非空の出力を返すこと（規律そのものは /refine:refine-docs の skill-md.md が定める）．「美の6条」の件数と全参照の一致 |
| 紹介 | 各プラグインの README.md が「構成」の定める形を持つこと．「導入」の対応先が `CLAUDE_CODE_ONLY` と，依存先が `dependencies` と一致すること．本書が `SHARED`（refine と heal）以外のプラグインを名指さないこと |
| 写し | `COPIES`（定型文の照合元）のキーの語を持つ配布文書（plugins/ 配下の Markdown）が，定型文を一字違わず持つこと．30字以上の同じ断片（句点・セミコロン・コロン・ダッシュで切った単位）が，`COPIES` に載らないまま二つ以上の配布文書に現れないこと |
| 配布文書 | 所有者の固有名・日付が無いこと．`ENV_EXEMPT` が挙げる文書を除く配布文書に，実行環境に固有の語（ツール名等）が無いこと |
| 書き方 | GitHub の描画で閉じない `**`，同じ文末の3連続，description の体言止めが無いこと |
| コミット | マージを除く全コミットメッセージの機械的な部分——件名の形式と長さ，件名と本文を分ける空行，本文の折り返し，ツールが注入するトレーラの不在（規律そのものは，コミットを提案するスキルの「文面の基準」と「固有の走査」が定める） |

声（文の調子）・因果・1コミット1意図は機械に判定できないので scan.py は担わない．

`python scripts/scan.py` で走らせると，検査ごとの対象件数を出す．対象が0件の検査は空振りとして違反に数える．違反が一件も無ければ exit 0 を返す．[CI](.github/workflows/scan.yml) は master への push と PR ごとに scan.py を走らせ，その結果を確定の根拠にする．コミットの検査に全履歴が要るので，リポジトリを `fetch-depth: 0` で取得する．

機械で捉えられる観点が増えたら scan.py に足す．足したら違反を1つ注入して落ちることを確かめる．除外を設けるなら理由をコメントに残し，除外が検出を殺していないかも確かめる．

### リリース

各プラグインは独立した SemVer 単位——利用者はプラグインを個別に導入するため，バージョンは変更のあったプラグインだけが上がる（lockstep にしない）．リリースではプラグインごとに上げ幅を判定し，`<plugin>-vX.Y.Z` 形式のタグと GitHub Release を個別に発行する．
