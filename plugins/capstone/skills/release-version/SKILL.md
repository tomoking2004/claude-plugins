## 手順

1. **前提確認**：デフォルトブランチが判明し現在のブランチと異なれば，切り替えを促して中断する．作業ツリーが汚れていれば中断し /capstone:commit-changes を促す．origin があれば `git fetch origin` し，ブランチが遅れていれば中断して取り込みを促す——bump とタグの後で rebase すると，タグが元のコミットに取り残される．
2. **リリース単位の判定**：バージョンフィールドを持つマニフェスト（`package.json`・`pyproject.toml`・`Cargo.toml`・`plugin.json` 等）をリポジトリ内で探し，マニフェストの置き場（マニフェストのあるディレクトリ．`.claude-plugin/plugin.json` は `.claude-plugin/` の親）を数える——同じ置き場のマニフェストは，幾つあっても一つに数える．以降の手順はリリース単位ごとに独立して行う．
   - **置き場が無い**：**単一パッケージ**（リポジトリ全体が一つのリリース単位）として扱う．版はタグだけが持ち，現バージョンは，その単位の直近のタグ（手順3が定める）の版である．
   - **置き場が一つ**：単一パッケージとして扱う．
   - **置き場が二つ以上で，どれも他の置き場を含まない**：**マルチパッケージ**（monorepo）とみなし，各置き場を独立したリリース単位とする．
   - **置き場が二つ以上で，ある置き場が他の置き場を含む**：どの置き場を単位とするかを問う．答えで単位が一つに決まれば単一パッケージ，二つ以上ならマルチパッケージとして扱う．他の単位を含む置き場を単位に選んだら，含まれる単位のディレクトリは，含む側の単位に数えない．
3. **対象と上げ幅の判定**：各リリース単位を，下の三つの語を使って，四つの場合（初版・変更なし・利用者に見える変更がある・利用者に見える変更が無い）に振り分ける——この順に確かめ，最初に成り立つ場合を採る．リリース対象に残る単位（対象単位）は，初版の単位，利用者に見える変更がある単位，見送らないと答えた単位である．対象単位が一つも無ければ，何も書き込まず，その旨を告げて終える——未 push のコミットがあれば，リモートへ届けるには push が要ることも告げる．対象単位では，バージョンの実体（マニフェストの `version` と，その単位の版を語る全参照箇所——配下のほか，ルートの lockfile 等，単位の外にあるものも含む）を特定する．
   - **その単位のタグ**（振り分けに使う語）：既存タグのうち，その単位の版を示すものをいう——単一パッケージでは版を示す全てのタグ，マルチパッケージではその単位を名指すタグである．どのタグがその単位の版を示すかを既存タグの命名（`git tag -l` で全件を見る）から一通りに読めなければ問う——単位を名指さないタグがある場合等．その単位の直近のタグは，その単位のタグのうち HEAD から辿れる最も近いものをいう．その単位のタグがあるのに HEAD から辿れるものが無ければ，どのタグをその単位の直近のタグとして扱うかを問う．
   - **その単位のコミット**（振り分けに使う語）：単位のパス（単一パッケージではリポジトリ全体，マルチパッケージでは置き場のディレクトリ）へ触れた，マージでないコミットのうち，HEAD から辿れて，その単位の直近のタグからは辿れないものをいう——`git log --full-history --no-merges <その単位の直近のタグ>..HEAD -- <単位のパス>…` で得る．その単位のタグが無ければ，その単位のコミットを HEAD から辿れる全てのコミットから選び，`git log --full-history --no-merges -- <単位のパス>…` で得る．単位のパスからは，手順2で含む側の単位に数えないとしたディレクトリを除く．置き場の外にあって，その単位の挙動か依存先を決める場所（共有のディレクトリ等）があれば，そのパスを加える．上の「直近のタグ」「どのタグからも辿れないコミットと変更ファイル」は，その単位の直近のタグ・その単位のコミットの代わりにしない——前者はその単位のタグ以外のタグも数える．後者はさらに，HEAD から辿れないタグも数え，単位のパスで絞らず，マージコミットも含む．
   - **利用者に見える変更**（振り分けに使う語）：その単位のコミットのうち，版を出して初めて，利用者（その単位を導入して使う人）の使うものを変えるものをいう．上げ幅の判定とリリースノートの取捨は，これだけを数える．導入・更新で配られて動くものの挙動（速さ・資源の消費を含む）か依存先を変えるコミットと，公開した版の中身を載せる頁（パッケージのレジストリ等）に出る文書を変えるコミットは当たる．保守する人しか使わないもの（道具・文書・試験・CI）だけを変えるコミット，挙動を変えない書き直し，ブランチから直接読まれるだけの文書を変えるコミットは当たらない．当否は中身で決め，種別では決めない——`feat`・`fix` でも当たらないことがあり，`docs`・`chore` でも当たることがある．複数の単位にまたがるコミット（リネーム等）は，触れた単位ごとに当否を決める．当否が割れるコミットは問う．
   - **初版**（その単位のタグが無い）：上げ幅は判定せず，マニフェストの現バージョンをそのまま初版の番号とする．現バージョンが仮値（0.0.0・0.1.0 等）か，マニフェストが無ければ，初版の番号を問う．
   - **変更なし**（その単位のコミットが無い）：リリース対象から外す．
   - **利用者に見える変更がある**（その単位のコミットに，当たるものがある）：上げ幅を，当たるものの中身から判定する——互換を破る変更があればメジャー（プレ 1.0 ではマイナー），機能を足す変更があればマイナー，どちらも無ければパッチ．Conventional Commits の種別（`feat`・`fix`・`perf` 等）と破壊的変更の印（`!`・`BREAKING CHANGE`）は目安に使い，中身と食い違えば中身を採る．1.0.0 昇格と，判断の割れる上げ幅は問う．
   - **利用者に見える変更が無い**（その単位のコミットはあるが，どれも当たらない）：版を出しても利用者の使うものが変わらないので，その単位の見送りを勧めて，見送るかを問う——当たらないとしたコミットとその理由を添える．見送った単位はリリース対象から外し，何も書き込まない．見送らないと答えた単位はパッチとする．その bump コミットの本文とノートは，「文面の基準」にある，利用者に見える変更が無いまま出す版の定めに従って書く．
4. **提案**：対象単位ごとに，新バージョン・上げ幅（初版には無い）・編集対象（バージョンの実体のうち，新バージョンと値が違う箇所）を示し，下の各項を全文で提案する．承認は全文に対して取る——既存の下書きを使う場合も全文を提示し，下書きの在処を示すだけでは足りない．「文面の基準」に従い，出す前に「固有の走査」を全件通し，**通した証跡を提案に添える**——照らした手本，裏取りした数値・URL，バージョンの参照箇所を探した範囲，利用者に見える変更に当たらないとしたコミットとその理由を，簡潔に．走査は成果物を残さないので，黙って飛ばしても外からは見えない；添えれば見える．通さなかった走査があれば，その旨と理由も書く．提案の時点の `git status --short`・`git rev-parse HEAD`・`git tag` の出力を控える．
   - **bump コミット**（件名＋本文）：編集対象があるときだけ作る．無ければ（現バージョンのまま出す初版で，バージョンの実体が揃っている場合等）作らない旨を示す．
   - **タグ**：名前は，その単位のタグの命名に倣う．その単位のタグが無ければ他の単位のタグの命名に倣い，それも無ければ単一パッケージは `vX.Y.Z`，マルチパッケージは `<置き場のディレクトリ名>-vX.Y.Z` とする——名前が一通りに決まらないか，他の単位のタグと区別できなければ問う．注釈を付けるかは上の「既存タグ一覧」の先頭のタグに倣い，付けるなら文面は上の「一覧の先頭のタグの注釈の全文」に倣う．タグが一つも無ければ注釈を付け，文面はリリースノートのタイトルと同じ1行にする．注釈も全文で提案する．
   - **リリースノート**（タイトル＋本文）．
   - **About 欄**（説明・website・topics）：現状を下の「文面の基準」の定めと突き合わせ，差分があれば新しい全文を提案する——リポジトリに一つの設定なので，対象単位の数によらず高々一度扱う．
   - **リモートリポジトリ**：origin が無ければ，その作成（名前・About 欄・公開範囲）と origin 設定を提案に含める——承認前に作らない．
   - **対象外の単位**：マルチパッケージでは，対象から外した単位（変更なし，または利用者に見える変更が無く見送り）も列挙し，見落としでないことを示す．
5. **承認**：平文の提案へのチャットの返信で受ける——選択式ダイアログは提案の表示を妨げるため使わない（承認でなく選ぶだけの問いは選択式でよい）．承認まで書き込まない．承認が覆うのは見せた内容だけである——提案の後に内容を変えたら（但し書き1つでも）示して改めて問い，見せていない他所の変更を含めない．修正指示は反映して再提案，意図の割れる箇所は問う．
6. **実行**：承認後，書き込みの直前に手順4のコマンドを打ち直して控えと比べ，違えば実行せず再提案し，一致すれば下の a〜g を一気に行う．マルチパッケージでは対象単位ごとに a〜c を繰り返し，全単位分が済んでから d 以降へ進む．bump コミットを作らない単位では，a・b を飛ばす．
   a. 編集対象を新バージョンに書き換え，`git grep` で旧バージョンの残存を確認する（単一パッケージなら全体，マルチパッケージなら，その単位のディレクトリと，単位の外にあるバージョンの実体に絞る——他単位は無関係な一致がありうる）．
   b. a で書き換えたパスだけをステージし，承認した全文で bump コミットを作る．
   c. 承認した名前でタグを打つ——bump コミットを作った単位ではそのコミットに，作らない単位では手順4で控えた HEAD に．注釈を付けるなら，承認した全文を注釈にする．
   d. origin へブランチと**今回打ったタグだけ**を push する（`git push origin <ブランチ>` に続けて `git push origin <タグ>…`）——`--tags` は今回のリリースと無関係な既存タグまで押し出す．origin が無ければ，承認済みの内容でリモートリポジトリを作成し origin に設定してから push する．
   e. About 欄に承認済みの差分があれば `gh repo edit --description "<説明>" --homepage "<URL>" --add-topic <topic>` で適用する（一度だけ．差分のある項目だけを渡し，除く topic は `--remove-topic` で渡す）．
   f. `gh` が使えれば（導入・認証済み）対象単位ごとに `gh release create <タグ> --title "<タグ> — <要点>" --notes "<本文>"` でノートを公開（非対話実行は notes 系フラグ必須）；使えなければタグ push で完了し理由を告げる．
   g. 書いたものだけを取り直し，承認した全文との一致を確かめる——bump コミットは `git log -1 --format=%B <コミット>`，タグの注釈は `git tag -l --format='%(contents)' <タグ>`，ノートは `gh release view <タグ>`，About 欄は `gh repo view --json description,homepageUrl,repositoryTopics`．

## 文面の基準

声（文の調子）・用語・言語は既存文（手本，無ければ README 等）に倣う——**手本を読んでから書く**．本節と「固有の走査」が，美の基準（refine プラグインの BEAUTY.md）をリリース文面という媒体へ具体化したもの——**両者を満たせば足り，実行時に他所を参照しない**．

- **bump コミット**：件名は手本に倣い，手本が無ければ単一パッケージは `chore(release): bump version to X.Y.Z`，マルチパッケージは scope を置き場のディレクトリ名にする；本文で上げ幅の根拠を簡潔に示す（初版では，その番号にした根拠を示す．利用者に見える変更が無いまま出す版では，利用者の使うものは変わらないことだけを書く）；測っていない程度の語（大幅に・劇的に等）を使わない．書式はコミットの既定に従う——件名は末尾ピリオド無しで50字以内を目安（上限72字），本文は72字以内で折り返す；トレーラは付けず，ハーネスが `Co-Authored-By`・`Claude-Session` 等を注入する規約であっても件名と本文だけを残す．
- **リリースノート**：タイトル `<タグ> — <要点>`；冒頭1行サマリ；変更の中身で分けたセクション（Features / Fixes / Performance…）の各項目は「**太字リード語** — 詳細」；破壊的・挙動変更は `## ⚠️ Behavior change` 節；関連 PR は `#N`；末尾に `**Full Changelog**: <compare URL>`（初版なら，タグまでの履歴の URL）．測っていない程度の語を使わず，公開後に測り直すと変わる値は数値で書かず増減の向きだけを書く．載せるのは**利用者に見える変更**（手順3が定める）だけで，当たらないコミットは種別によらず省く．取捨は手本に倣わず，この規則で判定する——手本のノートは，どのコミットを前にして何を落としたかを示さない．利用者に見える変更が無いまま出す版のノートは，タイトル・その旨の1行サマリ・`**Full Changelog**` の行だけにする．
- **About 欄**：説明は，リポジトリ全体を述べる既存の記述（ルートのマニフェスト等）があれば全文一致させ（単一の真実），無ければ新たに提案する．topics は同じ記述元の keywords 等に倣い GitHub の制約（小文字・数字・ハイフン）で揃える；website は実在の URL があるときだけ設定する．

## 固有の走査

- **リリース単位の正確性**：マルチパッケージで，上げる単位が手順3の対象単位だけか，変更なしの単位と見送った単位を巻き込んでいないか確かめる．
- **上げ幅は根拠を示す**：上げ幅が，利用者に見える変更に手順3の規則（互換を破る変更・機能を足す変更の有無）を当てた結果と一致することを確かめる．利用者に見える変更が無いまま出す単位は，パッチであることを確かめる．
- **単一の真実**：新バージョンがマニフェストと，手順3で特定した全参照箇所で一致する提案になっているか，実行前に照合する（手順6a の `git grep` は実行後の確認であり代わりにならない）．
- **事実照合**：件名・本文・リリースノート・About 欄の数値・URL・PR 番号は git/gh の実データで裏取りしてから書く．
- **様式踏襲**：書いた全文を手本（上の「一覧の先頭のタグが指すコミットの全文」「直近のリリースノート」，タグの名前と注釈の有無は「既存タグ一覧」，タグの注釈は「一覧の先頭のタグの注釈の全文」）と**並べて**，声・言語・書式・件名・タグ・構成が一致するか確かめる——記憶で照らさない．手本が無ければ既定に沿うかを確かめる．
- **取捨の説明責任**：その単位のコミット（手順3が定める）を一件ずつ辿り，利用者に見える変更に当たるものがノートに載っていること，当たらないものは理由（保守する人だけが走らせる，ブランチから直接読まれる等）を言えることを確かめる．当たらないとしたコミットとその理由は証跡に書く——ノートだけを見ても，落ちたものが規則によるのか見落としなのか区別できない．
- **列挙の対称**：リリースノートのセクション・箇条書きは順序原則を定め，粒度とリード語の付け方を揃える．
- **分離した走査**：リリースノートと About 欄は公開物なので，書き手の文脈を持たない検査役を観点（事実照合・目的・言語・本番の読み手）ごとに立てて走査させる——意図を渡さず，何をいくつ数えたかを報告させる．全文の読みは美の基準が変わった後と公開・提出の前にそれぞれ1回だけとし，経緯を知らない新しい役に任せる．他の周回（走査と直しの一巡）では，1人が走査を変わった文とその参照先に当てる．目的を定める文書は意図に数えず渡す．検査役の担当から，機械の走査がゼロを返した項目を除く．検査役が製品・ツールの公式文書と照合するのは，それを語る文が変わったときと全文の読みだけとする．検査役のゼロは，確定を差し止める指摘（止める指摘）のゼロを指す——事実の誤り・目的に答えていない・数えられる規則の違反・意味が取れないか二通りに読める・明晰さの欠け（一文に二つの事柄・息が続かない・同じ語の近接・字数合わせで痩せた）．この定義を指示へ写す．読み手の役には本番の読み手が持つものだけを渡す．検査役の指摘には確度（読みの確かさ）を高・中・低で付けさせ，「低」は止めず，書き手が判定して報告へ回す．止める指摘以外は採れるものを採り，残りは報告する．周回は3まで；止める指摘が残れば部分の手直しを重ねず，指摘のある単位を丸ごと目的に戻って書き直し，それでも消えなければ上流（方針・割り当て）を疑って問う．立てた役と渡した材料（立てられない環境ならその旨）は証跡に書く．
