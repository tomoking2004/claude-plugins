---
name: exec
description: 数十秒を超えて走るプログラム・スクリプト（学習・評価・データ処理・サーバ等）をログを残す形で起動し，異常の早期検知と完了報告まで担う．「実行して」「動かして」「学習を回して」など，スキル名の指定の有無に関わらず自動適用する．数十秒で終わる実行（テスト・ビルド・lint 等）は対象外とする．既に動いているものの状況を知りたいだけなら /ops:progress，UI を見た目で確かめたいだけなら組み込みの run スキルを使う．
---

対象：ユーザーが実行を求めたプログラム・スクリプトのうち，**数十秒を超えて走るもの**——学習・評価・データ処理・サーバ等，起動したまま会話を続けたり離席したりしうる実行．

このうち**常駐するもの**（サーバ・デーモン・監視プロセス）には「完了」が無いので，手順4・5（完了照合・完了通知）は落ちたときにだけ当てる．待ち方は手順2の「常駐するもの」の項が定める．

**対象外**：数十秒で終わる実行——テスト・ビルド・lint・ワンライナー・git 操作など，結果をその場で見て次の一手を決めるもの．通常のフォアグラウンド実行で足りる（/refine:code ・ /assignment:program 等が行う実行確認のうち，数十秒で終わるものはここに属し，本スキルを挟まない）．所要時間が読めなければまず短命として実行し，数十秒で返らなければ中断して本スキルで起動し直す．

## 手順

1. **寿命を決めて起動する**：セッション内・分離のどちらの形でも，ログ・終了コードの刻印は下の「実行の正典」に従う．
   - **セッション内**：1時間以内に終わると見込めるもの．Bash を `run_in_background: true` で起動する——ハーネスが完了時に通知する．コマンドの先頭で `mkdir -p logs; echo $$ > logs/<名前>.pid` を打つ（手順2が生存を読む）．**セッションを閉じるとジョブも終わる**．
   - **分離**：1時間を超えうるもの，またはユーザーの離席・セッション終了が見込まれるもの．親シェルから切り離し，セッションが閉じてもジョブを残す：

     ```sh
     mkdir -p logs; nohup sh -c '<コマンド> > logs/<名前>.log 2>&1; echo "ops-exit=$?" >> logs/<名前>.log' > /dev/null 2>&1 & echo $! > logs/<名前>.pid
     ```

     区切りは `;` であって `&&` ではない——`&&` で繋ぐと `&` がその AND リスト全体をバックグラウンドに送り，`echo $!` が `mkdir` より先に走って `logs/` 不在で落ちる（かつ `$!` がジョブでなくサブシェルを指す）．

     切り離せているかは，別の Bash 呼び出し（＝新しいシェル）からプロセスがまだ見えることで確かめる．

     この形はハーネスの完了通知を持たない——完了は手順2の待ちが `ops-exit=` で拾い，セッションが閉じた後は /ops:progress がログから復元する．迷ったら分離を選ぶ（ジョブを失わない側に倒す）．
   - **離席の備え**：分離が守るのはジョブだけで，手順2以降はセッションが生きている間しか働かない．結果の送信など，セッションが落ちても止めたくない後段があれば，`set -e` のスクリプトでジョブへ連ねる形を提案する．起動前に，離席後では手を打てないもの——資源の先客と空き（GPU・ディスク）・後段が使う認証——を確かめる．
2. **次の出来事まで待つ**：下のループを Bash の `run_in_background: true` で起動する——出来事があるとループは数行を出力して終了し，ハーネスが通知する．返ったら内容を確かめ，`ops-exit=`・`gone` でない限り `seen=` の値を渡して起動し直す．時間切れのある Monitor でなくこの形を使う——既読の位置を持ち越すので起動し直しても取りこぼさず，プロセスの消失と沈黙も捕らえる．`seen` の初期値は 0——ログの冒頭から読むので，起動直後の即死（import エラー・パス誤り・権限）がループの開始より前に起きていても見逃さない．

   ```sh
   log=logs/<名前>.log; pid=$(cat logs/<名前>.pid); seen=<既読の行数>
   while :; do
       kill -0 "$pid" 2>/dev/null; alive=$?
       lines=$(wc -l < "$log")
       sed -n "$((seen + 1)),${lines}p" "$log" | grep -E "<進捗マイルストーン>|ops-exit=|Traceback|Error|Exception|Killed|OOM|Segmentation fault|Fatal" && { echo "seen=$lines"; exit 0; }
       [ "$alive" -eq 0 ] || { echo "gone: ops-exit なしに消えた"; exit 0; }
       [ -z "$(find "$log" -mmin +<沈黙の上限（分）>)" ] || { echo "silent: ログが動かない"; echo "seen=$seen"; exit 0; }
       sleep 30
   done
   ```

   生存を読んでからログを読む順は崩さない——逆にすると，読み終えた直後に終わったジョブを `gone` と誤る．

   - **失敗を必ず捕らえる**：「今このジョブがクラッシュしたらこのループは何か言うか」を問う——言わないなら grep を広げる．`ops-exit=` は常に含める：これがあれば，正常終了も異常終了も沈黙のまま見過ごされることが無い．ハングと，包む `sh` ごと消える強制終了はこの行を書かない（本体だけが落ちれば非ゼロの値が刻まれる）——それを捕らえるのが `silent` と `gone` である．
   - **沈黙の上限**：マイルストーンの想定間隔の数倍に取る．ログが疎らなら `find` の行を資源の使用量（GPU 使用率等）の判定に替える．`silent` で返ったら様子を確かめ，生きていれば上限を延ばして起動し直す．
   - **進捗は間引く**：`<進捗マイルストーン>` に毎ステップ出る行を入れてはならない——出来事のたびにループが返り，会話を起こす．エポック完了・評価結果など，数分に1回程度のマイルストーンだけを選ぶ．
   - **常駐するもの**：起動を確認したら，待ちは異常だけを見張り続ける．沈黙が常態なので `silent` の行は外す．`ops-exit=` が出たら，それは正常終了でなく落ちた合図である．
3. **状況把握手段を案内する**：対象がライブダッシュボード・TensorBoard・進捗 URL 等を自分で提供していないか探す（生成される HTML/JSON，ログ冒頭の URL）．見つかればその URL を，無ければログの場所と所要時間の見積もり（過去の同種実行や進捗の速度から分かるとき）を一言で伝える．確認は求めず，伝えるだけでよい．離席が見込まれるなら届く範囲も告げる——通知はこのセッションが生きている間だけ出て，スマホへ届くのは Remote Control の接続時だけである．
4. **終了したらログ全文と成果物を照合する**：`ops-exit=` の値（またはハーネスの完了通知）を鵜呑みにせず，ログを実際に読んで裏取りする．完了時に生成されるはずの成果物（チェックポイント・出力ファイル等，特定できるとき）が実在するかも確かめる——ログにエラーが無いことは成果物の存在を保証しない．
5. **離席が見込まれたジョブには，成功・失敗を問わず完了時に1回 PushNotification を送る**：離れている間に終わったことこそ知らせるべき情報である．失敗ならどこで何が起きたかの要点を，成功なら主要な結果（accuracy 等）を一言で．ユーザーが今まさに会話中で見ているものには送らない．

## 実行の正典

- **シェル**：起動も監視も Bash ツール（Windows では Git Bash）で行う——POSIX のコマンドが両プラットフォームで通る．
- **バッファ**：Python は `PYTHONUNBUFFERED=1` を前に付けて起動する．リダイレクト先では出力がブロック単位で溜まるので，進捗が遅れ，`silent` が誤発火し，強制終了で出力が失われる．
- **ログ**：`logs/<名前>.log` にリダイレクトだけで書き出す（`> logs/<名前>.log 2>&1`）．`| tee` 等の中継パイプは付けない——パイプラインの終了コードは最後のコマンドのものになり，本体の異常終了が 0 にマスクされる．`logs/` が git 管理下に入るなら `.gitignore` への追加を促す（実行の痕跡であって成果物ではない）．
- **終了コードの刻印**：本体の直後に `echo "ops-exit=$?" >> logs/<名前>.log` を必ず続ける——これがログだけから完了・失敗を判定できる唯一の痕跡であり，手順2の待ちの完了シグナルであり，セッションが閉じた後に /ops:progress が拾う手掛かりになる．
- **起動は本スキルが行う**：ユーザーがターミナルで直接起動したプロセスの標準エラーは，ターミナルを閉じると失われ，後から追跡できない．

## 自己点検

- **対象判定**：数十秒で終わる実行に本スキルを被せていないか．
- **寿命判定**：離席が見込まれるのにセッション内の形で起動していないか．
- **待ちの広さ**：失敗シグネチャと `ops-exit=` を含み，クラッシュ時に必ず何か言うか．
- **待ちの細かさ**：進捗行が細かすぎて返りすぎないか．
- **待ちの継続**：`ops-exit=`・`gone` 以外で返ったのに，起動し直さず見張りを切らしていないか．
- **沈黙を成功と読まない**：完了は `ops-exit=` と成果物の実在で裏取りしたか．

## 制約

- **会話は止めない**：起動・監視の開始・案内（手順1〜3）を済ませたら完了を待たず，指示も待たずに通常の会話を続ける——手順4以降はジョブが終わった時点で働く．状況確認が来たら /ops:progress の手順で答える．
- **不可逆・有償・占有は起動前に承認を得る**：データの削除・上書き，本番環境への反映，課金の発生する実行（API の大量呼び出し・クラウド計算資源），GPU 等の長時間占有を伴うなら，何が起きるかを告げて承認を得てから起動する——バックグラウンドで走り出したものは取り消しが利きにくい．
- **実行内容は勝手に変えない**：コマンド・引数・設定が対象である．例外は実行の正典の「バッファ」の定めだけで，これはプログラムの挙動に影響しない．変える必要があれば問う．

/heal:skill を呼ぶ．
